# Provider、Skill 与 Model 关联详细设计（待评审）

日期：2026-11-27。本文依据当前 AtlasClaw 代码和已确认的交互原型编写，描述拟实现的行为；不代表后台功能已实现或已部署。

## 1. 已确认需求

1. 增加独立的「Provider 管理」菜单，与模型管理分开。
2. 可以全局启用、停用 Provider。
3. 可以分别配置 Provider、Provider 下属 Skill、与 Provider 平级的独立 Skill 所能使用的模型及默认模型。
4. 配置页只展示已添加的模型；通过「添加可用模型」窗口搜索、选择并添加，支持移除。
5. 默认模型只从该对象已添加的模型中选择。
6. 相关管理权限配置在 Role Management；初始仅管理员拥有，其他角色可以被授权。
7. 模型关联全局生效，不在角色中保存不同的关联，不增加个人覆盖配置。
8. 执行任务时继承用户已有 Provider、Skill 和上游业务权限。
9. 后续任务使用已保存的关联和最新有效模型凭据，无需重启服务。
10. 模型能力使用已有 capabilities 配置判断，不按厂商或模型名称硬编码。

## 2. 核心结论：谁选择 Skill，谁选择 Model

自然语言任务中的 Skill 选择仍由 LLM 参与规划，Core 校验该选择是否有效、是否在用户权限范围内。用户明确选择 Skill 或 Provider 后台工作流明确指定 Skill 时，直接执行指定目标，不再增加一次猜测目标的 LLM 调用。

Model 选择由 Core 按已保存的全局关联完成，不交给 LLM 自由选择服务商、端点和密钥。

同一个任务可以涉及不同模型。协调阶段使用模型 A，某个 Skill 的执行阶段使用模型 B。这里的切换通过独立的执行阶段实现，不修改共享 Agent 对象的 model 属性。

Skill 是指令和工具集合，不是一个模型进程。普通 Python 工具本身不会因为配置了模型而变成 LLM 调用；如果它无需推理，就继续执行现有本地代码。绑定决定理解 Skill 指令、执行其中模型任务及组织结果时使用哪个模型。

## 3. 三类关联对象与继承规则

| 对象 | 唯一身份 | 模型来源 | 默认行为 |
|---|---|---|---|
| Provider | provider_type + instance_name | 平台已配置的模型 | 未配置关联时保留平台默认行为 |
| Provider 下属 Skill | provider_type + instance_name + qualified_skill_id | 所属 Provider 允许的模型 | 继承所属 Provider |
| 独立 Skill | qualified_skill_id | 平台已配置的模型 | 继承平台默认模型 |

Provider 管理中以一行所代表的实例作为配置和启停粒度，同一类型的多个实例独立配置。安装目录和显示名称不作为关联主键。

Provider 下属 Skill 单独配置后，可以使用与 Provider 默认模型不同的模型，但必须先将该模型添加到 Provider 的允许范围。例如 Provider 默认 A、允许 A/B，下属 Skill 可以只允许 B、默认 B。

独立 Skill 不继承当前对话里最近使用的 Provider，也不受到无关 Provider 模型范围的限制。它直接使用自己的关联；未配置时使用平台默认。

Provider 下属 Skill 不额外叠加一个跨 Provider 的同名 Skill 全局策略，避免出现四层继承和同名冲突。

## 4. Role Management 权限设计

新增管理模块 provider_management，显示名称「Provider 管理」，包含：

| 权限 | 行为 |
|---|---|
| provider_management.view | 查看此菜单、Provider 状态、全局关联和独立 Skill 配置 |
| provider_management.enable_disable | 启用、停用 Provider |
| provider_management.configure_models | 添加、移除模型，设置默认模型，配置两类 Skill 的继承关系 |
| provider_management.manage_permissions | 在 Role Management 中管理上述权限；沿用现有权限治理约束 |

这些管理权限与现有 providers.provider_permissions、skills.skill_permissions 分开。管理关联不等于获得执行权限；能执行 Skill 也不等于能修改关联。

普通执行用户不需要 model_configs.view 或模型密钥管理权限。Core 可以代其按全局配置使用管理员保存的密钥，但 API 响应、Prompt、工具参数和执行结果均不返回密钥。

用于添加模型的候选接口单独返回安全元数据：模型引用、模型 ID、服务商、能力、启用状态及来源；不借用会返回可编辑凭据内容的接口。只有具有关联配置权限的用户能查询该候选接口。

现有多角色权限合并规则继续使用。角色只决定可见、可用的目标，不决定模型优先级。升级时管理员默认获得新管理权限；普通用户和现有自定义角色默认不增加权限。

前端菜单、按钮与后端 API 同时检查权限。直接请求后端不能绕过菜单隐藏。

## 5. 数据存储

复用现有数据库、ORM、迁移和审计日志，不新建服务，不把密钥复制进关联记录。

建议新增一张 capability_model_policies 表：

| 字段 | 用途 |
|---|---|
| id | 策略记录 ID |
| target_kind | provider / provider_skill / standalone_skill |
| provider_type | Provider 类型，独立 Skill 为空字符串 |
| instance_name | Provider 实例，独立 Skill 为空字符串 |
| skill_id | 注册表中的完整 Skill ID，Provider 级为空字符串 |
| enabled | Provider 的全局启停覆盖；Skill 记录不使用此字段 |
| model_mode | inherit / explicit |
| allowed_model_refs | 按显示顺序保存已添加模型的引用 |
| default_model_ref | explicit 模式下的默认引用 |
| revision | 并发保存校验，避免两位管理员相互覆盖 |
| updated_by / updated_at | 修改者与修改时间 |

唯一约束：(target_kind, provider_type, instance_name, skill_id)。服务端按 target_kind 校验哪些身份字段必须存在，不使用用户输入的任意文件路径或显示名称拼接身份。

模型引用示例：db-model:<数据库配置UUID>、file-token:<配置文件Token ID>。必须引用具体配置记录，不能只保存 model_id + provider，因为同一模型可能有不同账号、端点和密钥。

配置文件模型的引用不能使用当前展示 DTO 的 file:数组序号，避免文件调整顺序导致绑定改变。旧版凭据池中的模型通过统一模型目录适配其稳定 ID；没有稳定标识时不能生成按位置变化的持久引用。

未配置过的对象按兼容默认行为解析，不要求上线前给所有 Provider 和 Skill 手工建关联。

## 6. API 和保存规则

建议接口契约：

| 接口 | 用途 | 权限 |
|---|---|---|
| GET /api/provider-management/providers | 已安装类型、配置实例、启停和关联摘要 | view |
| GET /api/provider-management/providers/{provider}/{instance} | Provider 及下属 Skill 的完整配置 | view |
| PUT /api/provider-management/providers/{provider}/{instance} | 原子保存 Provider 和下属 Skill 的关联 | configure_models；启停发生变化时同时要求 enable_disable |
| PATCH /api/provider-management/providers/{provider}/{instance}/activation | 单独启停 | enable_disable |
| GET /api/provider-management/standalone-skills | 独立 Skill 列表和关联 | view |
| PUT /api/provider-management/standalone-skills/{skill_id}/model-policy | 保存独立 Skill 关联 | configure_models |
| GET /api/provider-management/model-options | 添加窗口的搜索与分页 | configure_models |

实际路由参数采用安全编码的注册表 ID；完整 Skill ID 可能包含命名空间，不依赖未经编码的斜杠路径。

候选接口支持查询文本、关联目标和分页，展示时排除已添加项；大模型目录不一次加载全部。仅“添加窗口”展示候选，不在配置页铺开整个目录。

服务端保存时验证：目标确实存在；Provider 与 Skill 的归属正确；模型引用存在且可用；下属 Skill 的显式范围属于 Provider 范围；默认模型属于已添加范围；能力匹配。explicit 空列表不能保存为可执行的模型配置。

删除正在被下属 Skill 显式引用的 Provider 可用模型时，不自动改写 Skill。保存返回具体受影响 Skill，管理员一起调整后原子保存。

保存只改变启停权限的请求不能顺带更改关联；只具备关联权限的请求也不能通过完整 PUT 改变启停状态。以字段差异检查，而非只检查按钮。

revision 不一致返回 409 并要求刷新，不静默覆盖。保存成功后返回最新版本、安全元数据和生效范围，并写审计日志。

## 7. 统一模型解析入口

新增 Core 级的 ModelBindingResolver（名称可在实现时按项目惯例调整），供聊天、Provider Agent Host、Provider 文本/图片桥接及 Skill 执行使用。

输入包含服务端认证用户、当前有效授权、可信的 Provider 实例身份、已验证 Skill ID、任务阶段、实际输入所需能力、任务和阶段 ID。客户端不能注入内部目标、候选 Token 集合、服务商地址和凭据。

解析结果包含 policy_id/revision、model_ref、有效候选范围、选中 Token、绑定来源和原因。Secret 仅停留在 Core 的调用对象中；用于日志和界面的是去除 Secret 的元数据。

选择步骤：

1. 在新任务入口检查 Provider 启用状态、用户 Provider/Skill 权限及实例可见范围。
2. 对 Provider 任务选 Provider 策略；对下属 Skill 选择显式 Skill 策略，否则继承 Provider；对独立 Skill 选其策略，否则平台默认。
3. 将策略引用映射到当前有效模型配置和凭据。文件与数据库的展示目录及可引用解析保持一致；文件模型不能仅因为数据库新增了另一模型就从显式关联中消失。
4. 根据 Skill 明确声明的要求和当前真实输入，过滤能力不匹配的候选。图片由 capabilities.vision 判断，不使用模型名字黑名单。
5. 默认模型符合要求且可用时优先。默认不适合本次输入时，仅从已添加且符合要求的模型中按现有健康、优先级策略选择，并记录选择原因。
6. 找不到候选时返回明确的配置/能力错误。不得脱离允许范围切换到平台其他模型。
7. 相同目标和策略下可以复用已选模型；进入另一 Provider/Skill 或策略发生变化时，旧的会话绑定不能阻止重新解析。

多模型允许范围不意味着每次随机切换。正常优先默认模型，只有能力不匹配或真实调用失败时才考虑范围内其他候选。不新增隐式字数、页数、Token、时长或调用次数限制。

## 8. Agent 如何启动和切换

### 8.1 已知 Provider，尚未确定 Skill

1. 后端确定 Provider 实例，不从用户文本中猜测实例身份。
2. 读取当前用户角色，生成其有权使用的能力目录。
3. 按 Provider 关联选择协调模型 A。
4. A 根据任务和已授权能力目录规划，选择 Skill S。
5. Core 验证 S 的身份、归属与用户权限。
6. S 若继承 Provider，则继续 A 或同范围内满足能力要求的模型；S 若绑定模型 B，则使用 B 执行该 Skill。

不能把角色允许的所有 Skill 的能力要求合并成一个总要求；只对本次实际执行的目标判断。

### 8.2 已知具体 Skill

用户明确选择 Skill，或 Provider 后台工作流明确指定 Skill 时，跳过模型猜测选择目标的步骤。Core 校验后直接选择对应模型执行，不必先调 A 再调 B。

### 8.3 普通聊天尚无明确 Provider/Skill

使用平台默认模型作协调模型。能力目录先按角色权限过滤，LLM 选择目标后 Core 再解析其关联。文本协调模型可以读取 Skill 描述并选择图片 Skill；图片正文只交给已验证的视觉执行模型，不先发送给不支持图片的协调模型。

### 8.4 推荐切换方式：以 Skill 执行阶段为边界

推荐“协调运行 + Skill 执行阶段”，不是在一个正在流式返回的模型请求中替换模型。

阶段 A：协调模型决定调用 S，产生经 Core 校验的执行目标。

阶段 B：Core 创建该 Skill 的运行上下文，使用 B、S 的指令及其允许工具完成执行。继续使用现有 AgentInstancePool 创建或获取与 B 匹配的实例，不修改共享 self.agent.model。

阶段 C：B 的结果、工具结果和产物引用返回调用方。若任务需要继续协调，则交回原协调模型 A；若是已明确的单 Skill 任务，直接交付 B 的结果，不增加一次 A 的复述调用。

每个 Skill 完成后，先把其输出提交到当前任务的共享上下文，再允许协调模型或后续 Skill 继续。后续 Skill 从原任务读取最新上下文，不从一个空白会话开始，也不只接收上一阶段的一句摘要。

用户只看到原任务的进度，不需要手工切模型，不新增可见会话。内部执行阶段有自己的 stage_id、父任务 ID、模型选择和用量记录。可复用现有内部会话机制，但不会把内部会话混入用户会话列表。

Skill B 又明确请求执行 Skill C 时，必须经过同一授权与关联解析入口。C 不因 B 的调用而自动获得权限。独立 Skill C 使用自己的模型策略，不自动继承 B 的 Provider。

### 8.5 为什么不推荐直接修改正在运行的 Agent

共享实例被多用户并发使用，直接赋值会让其他请求误用模型。已有工具调用还可能存在未完成的调用 ID、SDK 特有消息格式和不同模型的上下文要求。

阶段切换使用 Core 的规范上下文和调用边界，复用已完成的工具结果，不重新执行先前工具，不伪造或修改未完成工具调用的结果。当前在途 LLM 请求继续完成，Core 在下一个合法阶段边界切换。

同一模型的普通工具往返留在原 Skill 阶段，不拆成一连串新 Agent。只有实际切换 Skill 目标或进入不同模型任务时才增加阶段。

## 9. 上下文和结果传递

Skill 执行上下文包含：用户目标和明确约束、该 Skill 的指令、必要对话事实、输入文件引用、已有工具执行结果、当前用户身份与权限上下文、语言要求、父任务和阶段 ID。

不把另一模型的私有推理过程或 SDK 原生消息对象直接移交。对话与工具结果使用已有规范化消息结构；工具调用与结果必须配对。避免把不相关的其他 Provider 凭据和配置带进 Skill 上下文。

传递文档审核输入时，仍提交完整的所需脱敏报告、审核规范、检测标准和台账，不能因为切换模型而只传一个不完整摘要。文件、权限、工作目录和产物下载仍复用已有机制。

结果返回结构包括 status、output、artifacts、safe_model_usage、执行阶段引用。失败明确返回失败信息，不让协调模型把没有执行的步骤描述成已完成。

### 9.1 同一任务的共享上下文

上下文归属于用户会话和原任务，不归属于某个模型实例。模型切换、Skill 切换、内部阶段会话结束，都不清空任务上下文。

复用现有会话转录、文件存储和任务记录保存事实；以任务 ID 和阶段 ID 关联，避免复制整个工作目录或另建一套长期记忆系统。

| 共享内容 | 传递规则 |
|---|---|
| 原始任务与用户补充 | 保留原目标、明确约束、用户更正及语言要求，后续阶段读取最新有效要求 |
| 前序 Skill 输出 | 保留完整输出和结构化结果，标记产生结果的 Skill、阶段和执行模型 |
| 工具调用与结果 | 保留调用参数、完成状态、结果和调用 ID；模型切换不重新执行已完成工具 |
| 文件和资料 | 保留输入文件、已脱敏文件、参考资料的稳定引用和版本，后续阶段可通过已有文件工具读取 |
| 生成产物 | 保留 PDF、Markdown、截图、数据文件和下载引用，并记录来源阶段 |
| 执行状态 | 保留已完成步骤、失败步骤、待办项和需要用户补充的信息 |
| 来源与定位 | 保留页码、原文、标准依据和证据引用，不在交接时丢失可追溯信息 |

引用不是要求模型凭一个本地路径猜测文件内容。后续阶段通过 Core 的已有文件工具读取实际内容；显式文档审核请求所必需的脱敏正文和审核资料仍按现有流程完整提交。

### 9.2 Skill 之间的连续交接

示例：用户提出任务 → Skill S1 / 模型 B → Skill S2 / 模型 C → Skill S3 / 模型 D。

S1 完成后，将结果、证据和产物追加到原任务上下文；S2 读取原始目标及 S1 结果后执行；S2 完成后再次追加；S3 读取原始目标和 S1、S2 的有效结果。不是只把 S2 的最后一句回复交给 S3。

协调模型 A 在判断下一步时也读取同一份更新后的上下文。因此它知道已经做过哪些工作、上一步发现什么、还有什么没完成，不需要用户重新提供同一份资料。

进入后续阶段时保留用户意图和执行事实，同时加载当前 Skill 的指令和当前允许工具。前一个 Skill 的局部执行指令只作为历史记录，不继续充当下一个 Skill 的系统指令。

### 9.3 提交、恢复和失败处理

阶段输出以原任务 ID + 阶段 ID 幂等提交，并记录上下文版本。结果与阶段完成状态成功保存后，才进入下一阶段；重复收到同一完成事件不会重复追加结果或重复启动下一步。

服务重启或用户继续同一任务时，从持久化任务上下文恢复已完成阶段、文件引用和待办项。不能依赖已销毁模型实例的内存来维持连续性。

失败阶段保留此前已成功的结果，并明确记录失败状态。模型请求或外部写操作在重启时结果不明的，先使用现有执行证据核实状态；不承诺从中断的 Token 精确继续，也不因重试把未知结果的写操作再执行一次。

### 9.4 完整性和授权边界

跨模型传递规范化的对话事实、公开输出、工具结果和文件证据，不依赖模型私有推理。不同用户、不同任务的上下文不混用；进入下一 Skill 前重新检查当前执行权限，前序阶段结果不充当授权凭证。

脱敏要求在上下文交接中继续有效。下一个 Skill 不得因为拿到原始文件的本地引用，就绕过已有脱敏流程把原文发送到云端模型。

模型上下文容量变化时，完整任务记录和原文资料仍保留在本地。需要模型理解的前序结论及依据必须进入当前请求或可以由当前阶段实际读取；不能静默截断必要审核项目、证据或用户约束。若模型接口实际拒绝当前上下文，明确报告并保留恢复状态，不另加页数、字数等人为限制。

## 10. Provider 后台模型调用必须同样生效

当前 audit-report 使用 context.run_text 直接进行目录识别、项目审核和汇总，并不一定进入普通聊天的 Skill 选择器。只修改 Agent 启动模型会遗漏这条路径。

Provider 文本和图片桥接增加可验证的 skill_id 上下文。Core 已知 Provider 类型、实例和用户，再验证 skill_id 属于该 Provider 且用户有权使用。未提供 Skill 时应用 Provider 策略；明确提供 Skill 时应用其专属或继承策略。

audit-report 应把实际执行的 audit-report Skill ID 传给桥接。业务审核仍由现有 Skill 工作流负责，Core 只负责模型路由，不改写审核规则、脱敏、取证或报告生成逻辑。

同一个 Skill 的 run_text、run_visual 也要遵守实际能力过滤：是否需要图片取决于调用输入和声明，不因名字中有“报告”就推断一定需要视觉。

旧 Provider 不传 skill_id 的调用保持 Provider 级兼容行为。独立 CLI 如果绕过 Core 直接读取配置并调用模型，不会自动获得运行时策略；正式平台任务应走 Core 桥接，CLI 如需同等行为则必须显式接入同一解析契约，不能声称已覆盖。

## 11. 全局启停与热生效

数据库关联覆盖层作为全局业务启停依据，不能仅把数据库实例标为 inactive 后让 JSON 同名配置重新冒出来。文件模型和 Provider 原始文件不用被 UI 改写。

停用阻止新任务进入，同时从新的能力目录和用户 Provider 页面导航中移除相关入口。已接收的任务按已登记的运行上下文继续完成。用户执行权限撤销仍按授权检查处理，不因已有模型关联而绕过。

这里控制业务 Provider 的可用性，不通过卸载 Python 模块实现，也不顺带关闭其可能提供的登录或通道基础能力。

新任务和新 Skill 执行阶段读取已提交的最新策略。已开始的执行阶段保留自己的策略版本；已发出的模型请求不强制中断。凭据轮换在同一模型引用的下一次请求前刷新，不保留过期 API Key。

配置模型在执行前被删除、停用或缺少密钥时，显示具体错误；可用范围内还有符合能力要求的模型时才按策略切换，不越界回退。

数据库是各服务进程的共同依据，不能只更新当前进程内的字典。使用现有数据库读取边界和必要缓存失效，确保重启及多进程读取一致。

## 12. 错误和执行记录

错误包括：无管理权限、Provider 停用、Skill 未授权、模型引用失效、无兼容模型、凭据不可用、模型调用失败、保存版本冲突。返回可操作的具体对象信息，Secret 不出现在报错正文。

每个阶段记录：run_id、stage_id、parent_stage_id、user_id、Provider 类型与实例、完整 Skill ID、策略 ID 与版本、模型引用、模型 ID、服务商、选中原因、开始/结束时间和调用用量。

模型切换产生 model_binding_resolved / skill_execution_started / skill_execution_completed 事件。界面可展示“正在使用模型 B 执行报告审核”，但不显示 API Key 或私有推理。

缓存命中 Token 沿用已有用量结构。一个任务涉及 A、B 时分别记账并汇总到原任务，避免重复统计内部阶段。

## 14. 验收场景

1. 普通用户没有管理菜单权限；伪造 API 写请求返回 403，执行其已授权 Skill 不受此限制。
2. 在 Role Management 授权一个自定义角色后，该角色可以执行对应管理操作；只授予启停不能顺带修改模型。
3. Provider 默认 A、下属 Skill 专属 B：协调使用 A，实际 Skill 请求使用 B；返回后需要协调时仍使用 A。
4. 用户直接指定 Skill B 时，直接使用 B，避免无意义的 A 规划和复述请求。
5. 独立 Skill C 在 Provider 对话中被合法调用时使用自己的策略，不被误套 Provider 默认模型。
6. 文字任务不会因为用户还有视觉 Skill 权限就被强制分配视觉模型。
7. 视觉 Skill 不能使用未启用视觉的模型；能力符合的已添加模型可被选择，未添加模型不能成为隐式回退。
8. Provider 模型移除后，仍引用它的下属 Skill 产生具体配置提示；默认选择同步校验。
9. 新任务使用管理员刚保存的关联和刚轮换的 API Key，无需服务重启；已有任务不串模型。
10. 并发两个用户执行不同 Skill，不发生模型、权限、工具结果或文件串用。
11. 模型切换时已有写操作只执行一次；工具调用 ID 正确配对；失败不会被写成通过。
12. audit-report 的后台目录识别、逐项目审核、汇总实际请求均使用正确 Skill 关联，不只是聊天入口正确。
13. 停用 Provider 后新任务被拒绝；已有数据、产物和已接收任务不因卸载模块而丢失；重新启用恢复入口。
14. 文件模型顺序变化不影响关联；同名模型的不同凭据记录不会被错误合并；模型删除后的引用失效可追踪。
15. 搜索添加窗口支持分页、去重，配置页只展示已添加项；Provider、下属 Skill、独立 Skill 三种配置交互一致。
16. 迁移与服务重启后权限、关联、启停保持一致；旧任务默认行为兼容；内部阶段会话不显示在用户会话列表。
17. 连续执行 S1/B、S2/C、S3/D，S3 可以正确使用 S1、S2 结果与原始用户约束；协调模型同样能读取更新结果。
18. 跨 Skill 后页码、证据、脱敏文件、生成产物和下载引用保持有效；前一个 Skill 的系统指令不被误当成下一个 Skill 的指令。
19. 重复完成事件只提交一次结果、只启动一次后续阶段，已完成的工具写操作不会因为换模型或继续任务而重做。
20. 重启后可以恢复已完成阶段及待办上下文；前序失败明确保留，结果不明的在途写操作不会盲目重试。
21. 下一阶段重新检查用户权限，不能读取其他用户或无关任务资料，脱敏要求在跨 Skill 和跨模型时持续有效。

## 15. 实施拆分建议

1. 数据与权限：迁移、规范目标身份、全局策略服务、Role Management 模块、管理 API 和审计。
2. 基础模型解析：统一目录与稳定引用、继承、能力校验、默认选择、受限故障切换和凭据热更新。
3. 已知目标入口：明确 Provider/Skill 的任务、Provider 文本/图片桥接、audit-report Skill 身份接入。
4. 动态 Skill 执行：协调与执行阶段交接、结果返回、多 Skill 执行以及并发隔离。
5. 前端接入：使用已确认原型，接真实候选搜索与保存、权限控制、错误与并发保存提示。
6. 综合验证：真实调用确认 A/B 分别生效、独立 Skill 路由、后台审核、权限、重启和下载回归，再部署。
